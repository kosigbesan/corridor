00 / The uncomfortable truth
Most corporate travel emissions data does not arrive by API. It arrives as a scheduled CSV on an SFTP server, or a monthly PDF from a travel management company. The API is the aspiration, the file extract is the reality, and the product has to ingest both without pretending otherwise.

The itinerary itself lives one layer down, in a GDS passenger name record held by the TMC. Everything above it, the booking tools and expense platforms, is a reseller of that record. So the connector strategy is really three strategies stacked: reach the booking record, reach the HR record, and accept the file when neither is on offer.

The gate is commercial, not technical
Every one of these APIs is documented and standards-based. The hard part is permission. Concur lets a client read its own data with a Client Web Services SKU and no certification, but a resold app that appears in the App Center needs a signed Partner Agreement and a full certification project. Navan opens expense and user data but keeps bookings and webhooks behind partner access. Amex GBT requires an approved developer app. Amadeus closed its self-service portal on 17 July 2026, so GDS access now starts with a contract.

What the pipeline actually does

Four stages. The middle one, reconstruction, is the product. It is also the part a competitor cannot copy from a screenshot.

Ingest
  • OAuth connectors for live feeds
  • SFTP and CSV watchers
  • Idempotent by booking id
  • Back off on HTTP 429
Reconstruct
  • Card line to itinerary
  • Great-circle distance, 8% uplift
  • Cabin from fare class
  • Haul band from distance

  • DEFRA, ICAO, IATA factors

  • One canonical ledger
  • CSRD, SB 253, CDP export
  • Assurance trail
  • Ledger API

Connector notes

SAP Concur

OAuth 2.0, three data centers

Itinerary v4 is the Cat 6 feed. Scope travelallowance.itinerary.read. The legacy ITINER scope still appears for older integrations.

Token care: access token lasts one hour, refresh token six months. The base URI is geo-specific, so the connector has to store the returned geolocation per customer or calls fail.

Two doors: client-owned data needs the Client Web Services SKU only. A multi-tenant App Center listing needs certification.

Navan

Self-serve credentials

The easiest to start with. An admin creates API credentials under Travel, Settings, Integrations, then hands over a client id and secret.

Token at /ta-auth/oauth/token, scopes bookings:read users:read. Bookings come back under $.data[*], cursor paginated, with an includeTransactions flag for spend.

Limit: bookings and webhooks are gated to partner access, so a customer's own read is the realistic first step.

Amex GBT

Developer portal and certification host

OAuth 2.0 client credentials against the developer host, with a separate certification host for testing. The Get Trips API returns trips and their segments across air, hotel, car and rail.

Requires a registered account and an approved app. Egencia, the GBT brand, publishes thirteen public OpenAPI documents but gates the runtime, so contracts are readable before access is granted.

 

GDS, when you need the raw record

Amadeus, Sabre, Travelport

The PNR holds everything: segments, ticket numbers, fare class, sometimes aircraft type. A PNR conversion layer turns the raw record into structured JSON with distance and cabin already parsed.

Cost of entry: Amadeus needs an enterprise contract and certification. Sabre needs a pseudo city code and a signed contract. Travelport reports around $5,000 a year. Aggregators exist that reach all three through one interface, which is the pragmatic route for a small team.

HRIS, the Cat 7 backbone

Workday, BambooHR, Personio, ADP

Workday exposes custom reports as a web service through RaaS, authenticated by an Integration System User with basic credentials or an OAuth token. BambooHR, Personio and ADP use API keys or OAuth, and ADP has a dedicated address API.

The only fields that matter: home location, work site, working pattern, and a mode plus distance from a survey. Everything else is payroll noise.

Data minimisation

Home address is personal data

A home postcode is personally identifiable. Corridor geocodes it to a distance band at ingest and discards the raw address, then aggregates commute reporting at five or more employees per cell.

That is not only a privacy posture, it is what an assurer wants to see when the number is employee-derived.

When no API is on offer

The fallback ladder, in order of fidelity. A good product degrades gracefully rather than refusing the data.

1

Live API, itinerary level

Booking feed gives distance, cabin and mode. Tier one, primary data. This is the target state.

2

Scheduled file extract

Monthly CSV from the TMC over SFTP, or the platform's own bulk export. Same fields, lower cadence. Still primary data.

3

Expense and card spend

Dollars, not kilometres. Applies EEIO factors and tags the record secondary. Good enough to size the category, not to defend it.

4

Survey and national averages

For Cat 7 with no HRIS feed, a travel survey plus published commuting averages. Explicitly labelled as estimated.

Build order
Start with Navan and Concur, because a customer can authorise their own data without a partnership, which means a live pilot in days rather than months. Add Amex GBT next, since the app approval is the long pole. Treat GDS as a year-two investment, reached through an aggregator until volume justifies a direct contract. HRIS is self-serve and unblocks Cat 7 entirely, so it should ship alongside the first travel connector, not after.
